# Phase 6B.1 — Manufacturing business rules and acceptance specification

**Source and checkpoint:** [Phase 6A manufacturing audit](PHASE6_MANUFACTURING_VALIDATION.md), commit `4febf7fae5a18ba485213baccd43947a5d33ad85`. This specification uses fictional EMS data only. The 189 existing automated tests pass at this checkpoint. No manufacturer, engineer, buyer, production controller or quality practitioner has approved the proposed rules below.

## Purpose and decision boundary

This document turns the 13 Phase 6A scenarios into reviewable input records, hand calculations, current-behavior acceptance checks and explicit decision blockers. **Ready** means a case has an exact oracle for the current simulation or its fail-closed behavior. It does **not** approve a new manufacturing rule. **Blocked** means a proposed extension has no authorized rule or complete input contract; its future output must not be guessed.

The current interfaces directly used here are `calculate_plan` (`factoryflow/planning.py:16`), `calculate_material_timeline` (`factoryflow/material_timeline.py:22`), `calculate_capacity_plan` (`factoryflow/capacity.py:51`), `calculate_production_schedule` (`factoryflow/production_schedule.py:15`), and `calculate_ecn_plan` (`factoryflow/ecn_planning.py:193`). `BOMRevision`, `ECN`, `ProductionLot` and `StockHold` are defined in `factoryflow/ecn.py:33-181`. No execution posting interface exists. Use the pinned Phase 5C commit `bcf6c903fa5e71af9697b49fd22f5fd37e494634` as the no-regression comparison when implementation eventually starts; this specification does not change that baseline.

The following are **confirmed code behaviors**, not manufacturer-approved policies:

An approved future change supplied as scenario input may be used in a projection dated before its approval. A practitioner must decide whether a future application requires an approval-as-known-at-snapshot view. No such historical view is specified here.

## Acceptance gates for future development

1. **Policy gate:** Named EMS owners approve the exact business rule, data/status meanings, decision authority and negative cases. Unresolved outcomes remain marked **BLOCKED**; passing baseline tests cannot waive this gate.
2. **Oracle gate:** A reviewer independent of the implementation calculates expected quantities, dates, revisions, stock statuses and exceptions from frozen fictional inputs. Record arithmetic, assumptions and rule version. Do not use FactoryFlow output as the answer key.
3. **Architecture gate:** New inputs do not reinterpret old BOM, receipt or stock fields silently. One shared stock ledger, confirmed-only receipts, day-effective revision, whole-unit conservation, protected stock, no negative inventory and fail-closed dispatch/WIP remain explicit invariants.
4. **Automated gate:** Keep all 189 existing tests unchanged. Add positive, boundary and negative regression cases for the approved extension; compare exact daily output, component use, balances, trace and exceptions. Rerun full engine and dashboard suites, including no-ECN behavior.
5. **Human review gate:** Production/engineering/quality/buying inspect the scenario outputs and explanations for operational meaning. A separate observed planner trial records accuracy and time-to-task; no target is claimed until practitioners set it. Automated checks are not external industry validation.
6. **Release gate:** Review code and documentation diff, confirm no actual transaction capability was introduced unintentionally, retain a recovery point and verify the branch/commit. Any publication, integration or deployment needs its own authorization.

Phase 6B.1 is documentation only. No scenario here authorizes live purchasing, production completion, material issue, inventory adjustment, ECN approval, WIP release, or scrap/return posting.
